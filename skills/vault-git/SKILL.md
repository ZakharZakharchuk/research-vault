# Git у сховищі дослідження

Сховище (шлях — `vault_path` у `00_admin/config.md`) — це одночасно репозиторій і сховище Obsidian. У хмарній сесії воно доступне як змонтована папка, і саме монтування створює дві особливості, заради яких існує цей скіл.

## Залізне правило

**Повідомлення коміту пишуться англійською — завжди.** Заголовок і тіло. Усе інше в проєкті українською: нотатки, `CLAUDE.md`, протокол, звіти. Історія репозиторію — ні.

Це не стильова забаганка: історію читають інструменти, вебінтерфейс GitHub і потенційно інші люди, і змішана мова в `git log` робить її непридатною для пошуку.

## Формат повідомлення

```
<Imperative subject, ≤72 characters, no trailing period>

<Why the change was needed and what moved where. Not a list of files —
git already knows which files changed. Wrap at ~80 characters.>

<рядок атрибуції Claude, якщо середовище його задає>
```

- Заголовок у наказовому способі: `Move calibration facts out of CLAUDE.md`, не `Moved` і не `Moving`.
- Тіло пояснює **навіщо**, а не **що**: перелік файлів git покаже й сам.
- Якщо змінено кілька непов'язаних речей — це кілька комітів, а не один із маркованим списком.

## Push

**Із хмарної сесії push неможливий.** Проксі віддає `fatal: unable to access ... Received HTTP code 403 from proxy after CONNECT`. Це не полагодиться налаштуванням репозиторію.

Тому поділ праці такий:

- **Claude** готує зміни у файлах і робить коміт;
- **користувач** робить `git push` зі свого терміналу.

Після коміту завжди назвати користувачеві, скільки комітів чекає (`git status -sb` покаже `ahead N`), і дати готову команду. Не писати «запушено» — це неправда.

Якщо сесія запущена **на комп'ютері користувача**, а не в хмарі, мережа є і push працює звичайно. Тоді ж зникає й проблема з локами нижче.

## Локи: чому і що з ними робити

Змонтована папка забороняє видалення. Перевірено:

| Операція | Результат |
|---|---|
| створення, `O_CREAT\|O_EXCL` | працює |
| `rename`, зокрема поверх наявного файлу | працює |
| `flock` | працює |
| **`unlink`**, **`rmdir`** | `EPERM: Operation not permitted` |

Git знімає більшість своїх локів **перейменуванням** (`index.lock` → `index`), і це проходить нормально. Але:

- **`HEAD.lock`** — чистий вартовий. При коміті git блокує `HEAD`, проте переписує не його, а `refs/heads/<branch>`, бо `HEAD` символічний. Знімати такий лок нема куди перейменовувати — його треба **видалити**. Видалення падає, лок застрягає.
- **`.git/objects/*/tmp_obj_*`** — коли об'єкт із таким вмістом уже є, git видаляє тимчасовий файл замість перейменування. Теж застрягає. Шкоди немає, але накопичується.

**Наслідок каскадний:** один застряглий `HEAD.lock` обриває наступний коміт на півдорозі, і вже його `index.lock` іде шляхом відкату, тобто теж через видалення, і теж застрягає. Репозиторій заклинює мовчки — коміт «проходить», а насправді його немає.

### Порядок, який працює

**Спершу — чи можна видаляти.** Якщо в сесії є інструмент дозволу на видалення в підключеній папці (`device_request_delete_permission`), один раз попросити його для кореня сховища з поясненням «git залишає lock-файли, які знімаються лише видаленням». Після дозволу `rm` працює, і локи прибираються як звичайно (`find .git -name '*.lock' -delete` після кожної команди). Якщо інструмента немає або користувач відмовив — шлях нижче.

`mv` дозволений, тому осиротіле переноситься, а не видаляється. Прибирати **одразу після кожної git-команди, що пише**:

```bash
cleanup() {
  n=0
  for f in $(find .git \( -name '*.lock' -o -name 'tmp_obj_*' \) 2>/dev/null); do
    mv "$f" "_to_delete/$(echo "$f" | tr '/' '_')" 2>/dev/null && n=$((n+1))
  done
  echo "прибрано: $n"
}

git add -A;                cleanup
git commit -q -F msg.txt;  cleanup
```

Для читання використовувати `git --no-optional-locks` — тоді лок не береться взагалі:

```bash
git --no-optional-locks status --porcelain
git --no-optional-locks diff --stat
git --no-optional-locks log --oneline -5
```

### Перевірка після коміту

Обов'язкова, бо мовчазний провал — типовий сценарій:

```bash
find .git \( -name '*.lock' -o -name 'tmp_obj_*' \) | wc -l   # має бути 0
git --no-optional-locks log --oneline -2                      # коміт справді є
git --no-optional-locks status -sb                            # ahead N, дерево чисте
```

`_to_delete/` росте й лишається — Claude не може видалити й її. Періодично нагадувати користувачеві прибрати теку самому.

## Перед комітом

- **Переглянути `git --no-optional-locks diff --stat`.** У сховищі є файли, що змінюються самі: `00_admin/library.bib` — це автоекспорт Better BibTeX після кожної зміни в Zotero, а не чиясь правка. Якщо в діфі щось несподіване — назвати це користувачеві **до** коміту, а не після.
- **Не комітити наосліп `git add -A`, не глянувши на untracked.** У сховищі є ігноровані теки (`30_datasets/`, `_to_delete/`, робочі викиди `90_pipeline/out/*` крім `screening.md`), але нове може випасти повз правила.
- **Верифіковані нотатки.** Якщо в діфі є нотатка з `verified_by_human: true`, переконатись, що змінено подання, а не числа й висновки. Інакше зупинитись і запитати.

## Чого не робити

- Не писати повідомлення коміту українською.
- Не казати «запушено» після коміту з хмарної сесії — push там неможливий.
- Не запускати git без наступного прибирання локів.
- Не переписувати вже запушену історію (`--amend`, `rebase`) без прямого прохання.
- Не робити один коміт із кількох непов'язаних змін.
- Не намагатись видалити щось у змонтованій папці без дозволу — `rm` падає, замість цього `mv` у `_to_delete/`.
